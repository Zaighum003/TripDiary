1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) describes the functional and non-functional requirements for TripDiary, a Flutter-based personal travel journalling mobile application. This document serves as a reference for design, development, testing and assessment of the application for the Mobile Applications Development module (55-508210) at Sheffield Hallam University.

1.2 Scope
TripDiary is a mobile application targeting Android and iOS platforms via Flutter. The app enables users to:
• Create and manage trip records with photos and metadata
• Log diary entries enriched with camera photos, voice notes, and GPS location
• Set trip reminder notifications
• Perform voice search across entries
• Share entries with other applications
• Secure the diary with biometric or PIN authentication
The application does not require internet connectivity and uses no paid external APIs.

1.4 Overview
Section 2 provides an overall system description. Section 3 details all functional requirements mapped to mobile features. Section 4 covers non-functional requirements. Section 5 lists external interface requirements. Section 6 describes constraints and assumptions.



2. Overall System Description
2.1 Product Perspective
TripDiary is a standalone native mobile application. It operates fully offline; all data is persisted to a local SQLite database on the device. There is no backend server, cloud sync, or paid third-party API dependency.

4. Non-Functional Requirements
4.1 Performance
• The app shall launch to the home screen in under 3 seconds on a mid-range device
• Database queries shall return results within 500ms for up to 500 records
• Voice-to-text conversion shall begin within 1 second of microphone activation

4.2 Usability
• The UI shall follow Material Design 3 guidelines
• The app shall be responsive to screen sizes from 360dp to 600dp width
• All interactive elements shall have a minimum touch target size of 48x48dp
• Error messages shall be shown in Snackbar or Dialog with actionable text

4.3 Reliability
• The app shall not lose user data on unexpected termination (state preserved to DB on every write)
• The app shall handle permission denial gracefully without crashing
• All database operations shall use try-catch blocks with user-visible error handling

4.4 Security
• The app shall not store the user PIN in plain text
• All sensitive data shall be stored using flutter_secure_storage
• Camera, microphone and location permissions shall be declared in AndroidManifest.xml and Info.plist

4.5 Maintainability
• All code shall follow SOLID principles
• No widget shall exceed 250 lines; complex widgets shall be extracted to separate files
• The Repository pattern shall ensure all database logic is decoupled from ViewModels
• Minimum 60% unit test coverage on ViewModel and Repository layers

7. Constraints & Compliance
7.1 Technical Constraints
• Must be built using Flutter SDK and Dart only - no HTML, JavaScript or PHP files
• No paid external APIs may be used
• Must use local SQLite storage (sqflite) - no remote database
• Code must be 100% student-authored; no AI-generated code

7.2 Academic Constraints
• Architectural pattern used must differ from patterns implemented in class exercises
• All runtime permissions must be explicitly requested with rationale
• Automated tests must be included in the project submission
• A publishability report of no more than 500 words must accompany the submission
• An AI Transparency Declaration (AITS Level 1 - No AI) must appear in main.dart and report appendix
